---
title: "Meters"
description: "Configure grid, PV, battery, charge, and auxiliary meters in evcc."
---

Meters tell evcc how much power is flowing at each point in your home energy system. You define meters under the `meters:` key, give each one a name, and then assign those names in the `site:` and `loadpoints:` sections.

## Meter roles

evcc recognises five meter roles:

| Role      | What it measures                                                   |
| --------- | ------------------------------------------------------------------ |
| `grid`    | Import from / export to the public grid (positive = import)        |
| `pv`      | Power generated by your solar panels (positive = generation)       |
| `battery` | Power flowing into/out of a home battery (positive = charging)     |
| `charge`  | Power delivered to a vehicle at a specific loadpoint               |
| `aux`     | Auxiliary loads (e.g. heat pump) that reduce the available surplus |

<Note>
  A single physical device — such as a hybrid inverter — can appear as multiple meters with different roles. List it once per role under different names.
</Note>

## Assigning meters to site and loadpoints

After defining meters, assign them by name in the `site:` section:

```yaml
site:
  title: Home
  meters:
    grid: grid          # exactly one grid meter
    pv:
      - pv              # one or more PV meters
    battery:
      - battery         # one or more battery meters
    aux:
      - aux             # one or more auxiliary meters
```

For a dedicated charge meter on a loadpoint (useful when the charger has no built-in meter):

```yaml
loadpoints:
  - title: Garage
    charger: wallbe
    meter: charge       # must NOT be the grid or PV meter
```

## Meter types and protocols

evcc supports a wide range of protocols and device integrations. The most common are described below.

<Tabs>
  <Tab title="Modbus (mbmd)">
    The `mbmd` type uses the [mbmd](https://github.com/volkszaehler/mbmd) library to read Modbus RTU and TCP meters. It supports dozens of popular DIN-rail energy meters.

    ```yaml
    # Eastron SDM630 / SDM72DM-V2 via RS485-to-Ethernet adapter
    meters:
      - name: grid
        type: mbmd
        model: sdm        # SDM630 / SDM72DM-V2
        uri: rs485.fritz.box:23
        rtu: true         # RS485 device connected via Ethernet adapter
        id: 2
        power: Power      # Modbus register for total power (default)
        energy: Import    # Modbus register for imported energy (default: Sum)
    ```

    Common `model` values: `sdm` (Eastron SDM series), `janitza`, `abb`, `inepro`.

    For Modbus TCP (no RS485 adapter needed):

    ```yaml
    meters:
      - name: grid
        type: mbmd
        model: sdm
        uri: 192.168.1.50:502
        id: 1
    ```
  </Tab>
  <Tab title="SunSpec">
    SunSpec is a standard supported by many inverters (Fronius, SMA, SolarEdge, Kostal, and others). evcc reads SunSpec models 201/202/203 for meters and 101/103 for inverters.

    ```yaml
    # SunSpec meter reachable via Modbus TCP
    # (e.g. Fronius Smartmeter connected through the inverter)
    meters:
      - name: grid
        type: custom
        power:
          source: sunspec
          uri: 192.168.1.10:502
          id: 1
          value:
            - 201:W
            - 211:W
            - 203:W
        energy:
          source: sunspec
          uri: 192.168.1.10:502
          id: 1
          value:
            - 201:TotWhImp
            - 211:TotWhImp
          scale: 0.001
    ```

    <Tip>Use `evcc configure` to auto-detect SunSpec devices — it scans your network and fills in the URI and device ID automatically.</Tip>
  </Tab>
  <Tab title="HTTP / JSON">
    Many modern devices expose a REST or JSON API. Use the `custom` type with an `http` source and a `jq` filter to extract values.

    ```yaml
    # Fronius Solar API v1 — PV meter
    meters:
      - name: pv
        type: custom
        power:
          source: http
          uri: http://192.168.1.5/solar_api/v1/GetPowerFlowRealtimeData.fcgi
          jq: if .Body.Data.Site.P_PV == null then 0 else .Body.Data.Site.P_PV end
        energy:
          source: http
          uri: http://192.168.1.5/solar_api/v1/GetPowerFlowRealtimeData.fcgi
          jq: if .Body.Data.Site.E_Total == null then 0 else .Body.Data.Site.E_Total end
          scale: 0.001
    ```

    ```yaml
    # Shelly 3EM — grid meter
    meters:
      - name: grid
        type: custom
        power:
          source: http
          uri: http://192.168.1.20/status
          jq: .emeters | map(.power) | add
        energy:
          source: http
          uri: http://192.168.1.20/status
          jq: .emeters | map(.total) | add
          scale: 0.001
    ```
  </Tab>
  <Tab title="SMA">
    SMA Energy Meters and Home Managers broadcast data over multicast. evcc listens automatically — no polling required.

    ```yaml
    # SMA Energy Meter or Home Manager
    meters:
      - name: grid
        type: sma
        uri: 192.168.1.4    # IP address of the SMA device
    ```

    For a PV meter (reverse sign convention):

    ```yaml
    meters:
      - name: pv
        type: sma
        uri: 192.168.1.4
        scale: -1
    ```
  </Tab>
  <Tab title="Home Assistant">
    If you already have Home Assistant, you can use its sensor entities as meter sources:

    ```yaml
    meters:
      - name: grid
        type: homeassistant
        uri: http://homeassistant.local:8123
        power: sensor.house_power
        energy: sensor.house_energy

      - name: pv
        type: homeassistant
        uri: http://homeassistant.local:8123
        power: sensor.pv_power
        energy: sensor.pv_energy
    ```

    The `power` and `energy` fields take entity IDs. The power entity must return numeric watts; the energy entity returns numeric kWh.
  </Tab>
</Tabs>

## Template-based configuration

For supported devices, evcc provides pre-built templates so you don't need to write `custom` configurations by hand. Run `evcc configure` to select your device from the list, or use `type: template` with the template name:

```yaml
meters:
  - name: grid
    type: template
    template: eastron    # Eastron SDM630 / SDM72DM-V2
    usage: grid
    modbus: rs485
    host: rs485.fritz.box
    port: 23
    id: 2
```

## Battery meter configuration

Battery meters additionally report a state of charge (`soc`). For devices that support active battery control (holding charge, forcing grid charging), evcc can also send `batterymode` commands.

```yaml
# sonnenBatterie — grid, PV, and battery meters
meters:
  - name: grid
    type: custom
    power:
      source: http
      uri: http://192.168.1.30:8080/api/v1/status
      jq: .GridFeedIn_W
      scale: -1   # reverse sign: positive = import

  - name: pv
    type: custom
    power:
      source: http
      uri: http://192.168.1.30:8080/api/v1/status
      jq: .Production_W

  - name: battery
    type: custom
    power:
      source: http
      uri: http://192.168.1.30:8080/api/v1/status
      jq: .Pac_total_W
    soc:
      source: http
      uri: http://192.168.1.30:8080/api/v1/status
      jq: .USOC
```

## Modbus proxy

If an external program (e.g. a solar monitoring tool) already holds the Modbus connection to a device, evcc can share that connection through a built-in Modbus proxy:

```yaml
modbusproxy:
  - port: 5200
    uri: solar-edge:502
    # rtu: true    # set if the downstream device is RTU/RS485
    # readonly: true
```

evcc listens on `port` and relays requests to `uri`. Your other software connects to evcc's proxy port instead of the device directly.
